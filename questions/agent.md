## A1 你的调度器是什么？——云端—本地、智能—成本、延迟—成功率

### 引文版本一

云端—本地、智能—成本、延迟—成功率，这是当前通用 agent 系统不得不同时面对的三组现实张力。OpenRouter 的答案是 Fusion API：让多个模型并行分析，再由 judge 汇总；新版 Kimi Code 的答案是 `/tower` 和 secondary model：一边把子代理分发到云端隔离沙箱并行执行，一边把不同环节路由给不同档位的模型；DeepSeek Harness 给出的参照则是"Agent = Model + Harness"——工具、环境、权限、插件与模型本身解耦。
请注意：**它们都在回答 agent 系统如何变强，但并没有回答同一个问题。**如果让你基于 Kimi Code / DeepSeek Harness 这类 coding harness，设计一套新的通用 agent 框架，你的框架是怎样的？请给出：
1. **框架分层与数据流**：控制平面、执行平面、验证平面、记忆/上下文、工具权限分别在哪儿；
2. **调度策略**：什么时候本地、什么时候云端；什么时候小模型、什么时候大模型；什么时候单 agent、什么时候多 agent；什么时候单模型、什么时候模型合议；哪些情况明确**不多 agent**；
3. **三组张量的取舍**：成本、延迟、成功率如何进入同一张调度表；固定预算和延迟上限下，你必须牺牲什么；
4. **主 agent 的 system prompt**：必须写出可直接使用的完整文本，而不是描述它会写什么；它如何表达任务边界、工具权限、升级规则、验证规则与停止条件；
5. **prompt 与 harness 的分工**：哪些约束只能由 harness/代码保证，不能写进 prompt 里祈祷模型遵守？为什么；
6. **场景走查**：从校园办事助手、自动提 PR 机器人、20 篇文献调研报告中任选一个，说明一次任务从进入、路由、执行、验证到交付的完整路径。
请以"框架图或模块表 + 路由/降级规则 + 主 agent system prompt + 评估方案"提交。你可以借鉴 Kimi Code、DeepSeek Harness、OpenRouter Fusion，但必须声明：**我继承了什么、放弃了什么、为什么。**

**配套材料（读轴即可，不要求背数）**：最新 AA 全模型智能指数—成本点图（`AA_latest_all_models_intelligence_vs_cost.png`）、OpenAI GPT-5.6 系列 Coding Index—成本图（`OpenAI_AA_Coding_Index_cost_GPT-5.6_family.png`）、SEC-Bench Pro 多智能体延迟—成功率图（`OpenAI_SEC-Bench_Pro_multi_agent_latency.png`）、SEC-Bench Pro 多智能体成本—成功率图（`OpenAI_SEC-Bench_Pro_multi_agent_cost.png`）。
